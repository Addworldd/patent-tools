# 专利文本「可批注单文件」流程

把一份中英对照 md 变成**一个 HTML 文件**：双击就能打开，划选文字加高亮、写备注，批注存本机浏览器；需要收集他人批注时，让对方「导出批注」发你，你「导入批注」合并。

**零依赖**：单个 `.html` 文件，无 CDN、无网络请求、无后端。可以微信发、邮件发、U 盘拷，断网也能用。

## 何时用

- 要把对比文件/权利要求/CC 表发给他人阅读，并希望**收回他们的批注**
- 环境不允许联网、不允许部署服务
- 需要一个**随手可发**的文件（一个附件，不是一个链接）
- 同一份材料要在几台设备间来回看

不适用：需要**多人实时**看到彼此批注。单文件是异步汇总，不是实时协作；那种场景需要后端。

## 产出

| 产出 | 说明 |
|---|---|
| `XXX_可批注.html` | 单个文件，约 120–200KB（视文档长度），双击打开 |
| 批注 JSON | 用户点「导出批注」得到，用于换设备或收集他人批注 |
| 批注 MD | 用户点「导出 MD」得到，可直接贴进报告 |

## 🚀 最快上手：输入智慧芽分享链接一键生成（推荐）

现在支持直接输入**智慧芽免登录分享链接**（报告或智慧芽中导出的链接，含 `patentId`、`shareId`、`signature` 等参数），脚本自动完成浏览器鉴权、提取权要与说明书原文、段号、中英双语、段落核对并编译单文件 HTML。

```bash
python "<skill>/scripts/run_share_pipeline.py" "<你的智慧芽分享链接>"
```

### 一键流水线自动处理的五件事：
1. **智能浏览器自适应**：自动检索本机系统 Google Chrome 或 Microsoft Edge，免额外配置 Chromium，无头极速运行。
2. **免登录签名流转**：以 `/patent-view/abst`（摘要页）为初始入口完成签名鉴权，提取公开号（PN）、专利发明名称、申请人及公开日。
3. **权利要求提取**：访问 `/patent-view/clms` 抓取权利要求各权项原文，外文文献自动切换机翻并提取中文对照，按权项号对齐（如 `【权1】`、`【权2】`）。
4. **说明书与段号提取**：访问 `/patent-view/desc` 抓取说明书各段原文及段号（`[0001]`、`[0002]`...），外文文献自动提取机翻对照，并执行严格的连续性自检（`continuity`：无缺口、无重复）。
5. **产出完备交付包**：
   - `XXX_中英对照_可批注.html`：零外部依赖的单文件，双击即开，支持权要与说明书段落的高亮与备注，自带快捷跳转。
   - `XXX_全文_中英对照.md`：标准格式的归档 Markdown，随时可供审阅或自译润色。
   - `XXX_patsnap_raw.json`：原始抓取数据结构。

### 命令行下的翻译来源策略（四种选择）：

| 模式 | 参数示例 | 适用场景与机制 |
|---|---|---|
| **1. 智慧芽机翻（默认）** | `--trans-mode patsnap`（默认） | **全自动零配置**：Playwright 在后台自动点击智慧芽语言切换栏并拉取官方中文机翻，适合快速浏览大意。 |
| **2. 挂接外部自译/AI翻译** | `--zh-json "自译.json"` | **最高质量**：传入自定义键值对 JSON（`{"权1":"...","0001":"..."}`），直接覆盖机翻，确保法律术语严密。 |
| **3. Agent / AI 对话即时翻译** | 命令行出骨架后交由 Agent 翻译 | **无缝人机协作**：先由脚本抓取英文原文，在对话中让 Agent 逐段按专利规范翻译并回填编译。 |
| **4. 纯原文骨架模式（待补）** | `--trans-mode empty` | **纯手工自译流**：不拉取机翻，译文行保留 `（待补）`，生成 md 供译员逐段线下填写。 |

## 前置：外文专利怎么变成素材

**外文专利（美/欧/日/韩等）不能直接做成 HTML**，必须先变成「中英对照 md」。这一步是本 skill 的起点。

### ⚠️ 外文文献四条硬规矩（不可跳过、不可打折）

| # | 规矩 | 为什么 |
|---|---|---|
| 1 | **原文逐字照抄** | 不改字、不缩写、不"顺一下"；段号沿用智慧芽英文侧归一的 `【00xx】` |
| 2 | **译文自己翻，不用机翻** | 智慧芽 / 浏览器自带机翻**只当看懂大意的辅助**，一个字都不许进 md |
| 3 | **中英逐段对照** | 一段一对照，不合并、不拆散；段号左右必须对齐 |
| 4 | **段落必须核对，不许漏段缺段** | 漏一段就可能漏掉一个技术特征，后面的对比结论全部作废 |

第 2 条的道理：机翻会把 `inserted completely into the vaporizer body` 译成「完全插入蒸发器主体」，读者立刻以为烟弹被外壳吞了；实际是插进**接收部**、吸嘴仍在外面。**你要批注的恰恰是这种结构关系，机翻一错，批注就是在错的地基上盖楼。**

第 4 条不靠"看一遍"保证，靠脚本断言。`mk_bilingual_md.py` 会输出 `continuity` 块：

- `gaps` 必须为 `[]`
- `found` 必须等于 `expected`（`段号上限 - 下限 + 1`）
- `duplicates` 必须为 `[]`

**有任何一项不满足，脚本以退出码 2 中止。此时停下补段，不要带缺口往下做。**

### 情形 A：手头已有中英对照 md（最省事）

直接跳到「三步流程」，但**入门先过核对闸**：

```bash
python "<skill>/scripts/check_md.py" "你的md.md" --expect 125
```

`gaps` 非空、`duplicates` 非空、或 `untranslated` > 0 的，一律不许进第 1 步。
`--expect` 填你确知的原文总段数（不知道该值就省掉，脚本仍能自证连续性）。

### 情形 B：从智慧芽取数（最常用）

#### B-1 先取英文原文，出一份带核对结果的骨架

```bash
python "<skill>/scripts/mk_bilingual_md.py" \
  --en "<智慧芽导出的英文JSON>" \
  --pn "US20160183596A1" \
  --out "US20160183596A1_全文_中英对照.md"
```

此时译文行全是 `（待补）`。**先看 `continuity`，确认段落齐了再译** —— 不要拿一份缺段的稿子去翻译，白译。

#### B-2 逐段自己译，再合并

两种写法，选一种：

- **直接改 md**：把每段的 `　　**译**：（待补）` 换成你的译文
- **另存 `zh.json`**（`{"0001":"中文…","0002":"中文…"}`）再合并：

```bash
python "<skill>/scripts/mk_bilingual_md.py" \
  --en "<英文JSON>" --zh "<自译译文JSON>" \
  --pn "US20160183596A1" --out "US20160183596A1_全文_中英对照.md"
```

> `--zh` 只接受**你自己译的** JSON。智慧芽机翻的 `zh_*.json` 不要直接塞进来 ——
> 脚本会检查每段中文占比，译文里几乎没有汉字的段会被列进 `zh_suspect`，那就是没译或只译了一半。

**这句话要说白话**：`zh_suspect` 只能查"有没有译"，**查不出"是不是机翻"** —— 机翻出来的也是中文，汉字占比完全正常。
所以第 2 条规矩没有任何技术兜底，全靠执行的人守住：**机翻稿只能放在旁边对照着看，落进 md 的每个字必须自己写。**
（这一步没有捷径。审阅方拿你的译文判断技术方案，翻错一个连接关系就是误导，而且错误会一路传到报告的对比结论里。）

#### B-3 交付前必须看到的三行

```json
"continuity": {"range":"0001-0125","expected":125,"found":125,"gaps":[],"duplicates":[]}
"untranslated": 0
"zh_suspect": []
```

三个都是干净值，这份 md 才允许进第 1 步。

**输入 JSON 形态**（脚本自动识别）：

| 形态 | 结构 |
|---|---|
| 含 items 包装 | `{"items":[{pn, title, paragraphs:[{no,text}]}]}` |
| 单件 | `{"pn":..., "paragraphs":[{no,text}]}` |
| 纯数组 | `[{no,text}, ...]` |
| 译文 | `{"0001":"中文…","0002":"中文…"}`（按段号索引） |

**脚本自动处理的四件事**：

1. **剔除英文 JSON 里混入的机翻中文段** —— 智慧芽 `paragraphs` 常见「前一半英文、后一半同段号机翻中文」，一份 US20160183596A1 拉下来 250 条其实只有 125 个真实段。脚本按中文占比判断（>15% 视为中文段）并丢弃，同段号保留首次出现的英文。**注意：丢弃是丢掉污染源，不是把机翻当译文用。**
2. **截断 `【翻译】` 标记** —— 部分段内嵌机翻，只取标记之前的英文。
3. **检出段末小节残留** —— `BACKGROUND` / `SUMMARY` / `BRIEF DESCRIPTION OF THE DRAWINGS` 等 DOM 残留，默认**保留并列出清单**（不改原文）；要删加 `--strip-tail`。
4. **段落连续性核对** —— 输出 `continuity`：段号区间、应有段数、实有段数、缺口列表、重复列表。有缺口直接退出码 2。

**要不要分组**：给 `--groups groups.json` 可按段号范围切出 `## G3 · 系列一` 这样的分组标题：

```json
[{"from":"0001","to":"0008","name":"G0 · 交叉引用"},
 {"from":"0045","to":"0057","name":"G3 · 系列一 · 一体式烟弹"}]
```

### 情形 C：从 PDF 或纯文本

先手工整理成段落块格式（见下），或让上游把 PDF 提取结果映射成 `{no, text}` 的 JSON 再走情形 B。

PDF 这条路**最容易漏段**（跨栏、表格、附图说明文字常被吞），所以段落核对更不能省。整理完先跑一次核对：

```bash
python "<skill>/scripts/check_md.py" "你的md.md" --expect 125
```

输出 `range` / `expected` / `found` / `gaps` / `duplicates` / `untranslated`；有缺口就以退出码 2 中止，附带缺口段号清单。

> **外文专利的取证口径**：对比文件的公开内容只取**说明书具体实施方式**，不引其权利要求。
> 段号用智慧芽英文侧归一的 `【00xx】`，摘录时给段号，不改字。

## 素材格式（下游脚本的硬要求）

来源 md 必须满足「段落块」结构，这是定位的基础：

```markdown
## G3 · 系列一（分组标题，可省）

### 【0054】

> 英文原文（多行以 "> " 开头）

　　**译**：中文译文
```

关键约束：

- 段号形如 `### 【0054】`，**四位数字**
- 英文行以 `>` 开头，中文行以 `　　**译**：` 开头
- 段号唯一，不可重复
- `==…==` 会被转成预置高亮

## 三步流程

### 第 0 步（仅外文专利）：取数 JSON → 中英对照 md

**0-1 出骨架（含段落核对）**

```bash
python "<skill>/scripts/mk_bilingual_md.py" \
  --en "<英文JSON>" --pn "US20160183596A1" --out "XXX_全文_中英对照.md"
```

**0-2 自己译，译完合并**

```bash
python "<skill>/scripts/mk_bilingual_md.py" \
  --en "<英文JSON>" --zh "<自译译文JSON>" \
  --pn "US20160183596A1" --out "XXX_全文_中英对照.md"
```

**0-3 过核对闸（漏一步都不许往下走）**

```bash
python "<skill>/scripts/check_md.py" "XXX_全文_中英对照.md" --expect 125
```

要求：`gaps: []`、`duplicates: []`、`untranslated: 0`。任一不满足 → 回去补，不带缺口往下做。

已有中英对照 md 的直接从 0-3 开始。详见上一节。

### 第 1 步：解析 md → data.json

```bash
python "<skill>/scripts/parse_md.py" "<你的md路径>" --out "data.json" --doc-id "US20160183596A1"
```

自检：输出的 `paragraphs` 应等于 `check_md.py` 的 `found`；`duplicates` 与 `empty_en/empty_zh` 应为空。

### 第 2 步：生成单文件 HTML

```bash
python "<skill>/scripts/build_single.py" \
  --data "data.json" \
  --out  "US20160183596A1_可批注.html" \
  --doc-id "US20160183596A1"
```

脚本会自检：无残留占位符、无任何外部引用（`<script src>` / `<link>` / `http(s)://`），并回报体积与段数。

产出即可直接发给对方。

## 使用方式（告知用户）

| 操作 | 方法 |
|---|---|
| 加高亮 | 划选文字 → 弹出工具条 → 点「加高亮」 |
| 写备注 | 加完高亮自动弹出编辑框；或点已有高亮重新编辑 |
| 存批注 | 点「保存」，存本机浏览器（同一浏览器同一文件再次打开还在） |
| **改批注人** | 顶栏「批注人：xxx」按钮 → 输入新名字 → 可选把已有批注一并改名 |
| 单条改批注人 | 打开该高亮的编辑框，编辑框里有独立的「批注人」输入框 |
| 换设备 | 「导出批注」→ 发文件 → 对方「导入批注」 |
| 收回批注 | 让对方导出 JSON 发你，你导入后点「导出 MD」出汇总表 |

### 批注人（作者名）说明

- **首次加高亮时会弹框问名字**，留空记作「匿名」
- 之后不再追问，用记住的名字
- **随时可改**：点顶栏的「批注人」按钮
- 改名时可选「是否把已有批注一并改名」——不想动旧的选取消即可
- 每条批注的批注人**独立存储**，所以可以一条条单独改（编辑框里改）

修改的是 `annotations` 里每条批注自带的 `author` 字段，不影响批注位置和备注内容。

## 关键约束

### 批注跟着「浏览器 + 文件来源」走

localStorage 以文件来源为作用域。注意：

- **同一台电脑、同一浏览器、文件路径不变** → 批注还在
- **文件改名或移动目录** → 浏览器视为新来源，**看不到旧批注**（导出过的 JSON 仍可导入回来）
- **换浏览器/换电脑** → 不同步，必须走导出/导入

建议：文件生成后不要改名；要改名前先「导出批注」。

### file:// 下的浏览器差异

双击打开是 `file://` 协议。Chrome/Edge 允许 `file://` 下用 localStorage 且持久；Safari 对 `file://` 更严格，可能不持久。
若要跨浏览器稳妥，把文件放到任意静态服务器或云盘直链打开，来源变成 `http(s)`，localStorage 更稳定。

### 高亮位置用纯文本偏移

`mark_key` 格式为 `段号|侧|起|止`，偏移是**纯文本字符偏移**，不是 HTML 偏移。
因为页面渲染会插入 `<mark>` 标签，用 HTML 偏移会导致新增高亮后旧高亮全部错位。

### 跨段选择不支持

划选起止必须落在同一段内（同一 `data-no`），跨段自动放弃。跨段高亮没有明确锚点，刻意不支持。

### 导出/导入的合并规则

导入时按 `mark_key` 匹配：

- 不存在 → 新增
- 已存在且导入的备注非空 → 覆盖
- 已存在但导入的备注为空 → 保留原备注（不误删）

## 与「云端版」的区别

| | 单文件版（**默认**） | 云端版（备选） |
|---|---|---|
| 部署 | 无需部署，一个文件 | 需开通云服务 + 发布 |
| 多人实时 | ❌ 异步汇总 | ✅ 打开即见彼此批注 |
| 收回批注 | 对方手动导出 JSON | 你直接读数据库 |
| 离线 | ✅ 完全可用 | 需先联网打开过 |
| 适用 | 发给 1–5 人评审 | 团队长期协作 |

云端版模板与脚本保留（`templates/page_cloud_backup.html`、`scripts/build_html.py`、`scripts/export_notes.py`），需要时可恢复。
云端版要求：PostgreSQL 表 + GRANT + RLS 两道门（见 `references/cloud-schema.md`），且 `endpoint` 必须是已发布域名，未发布时任何请求都返回 401。

## 自检清单
