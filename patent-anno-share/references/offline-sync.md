# 离线可用与同步策略

## 结论

**可以离线查看和编辑，联网后自动/手动同步。** 前提是：该浏览器**至少联网打开过一次**该页面
（这样本地才有数据快照和代码缓存）。

## 三种状态

| 状态 | 能查看 | 能编辑 | 数据去向 |
|---|---|---|---|
| 在线 | ✅ 实时云端数据 | ✅ | 直接写云端 |
| 离线（曾打开过） | ✅ 本地缓存快照 | ✅ | 写 localStorage，入待同步队列 |
| 离线（从未打开过） | ❌ 页面本身打不开 | ❌ | — |

第三种是物理限制：页面要从服务器加载。若确需**首次离线**就用，得让对方先联网打开一次。

## 本地存储的三个键

| 键 | 内容 | 作用 |
|---|---|---|
| `anno.cache.<docId>` | 云端数据快照 | 离线时渲染用 |
| `anno.queue.<docId>` | 待同步操作队列 | 记录离线期间的增删改 |
| `anno.mine.<docId>` | 本地新增/修改的批注 | 叠加到快照上，本地优先 |

按 `docId` 分开，同一浏览器放多份文档互不干扰。

## 同步时机

1. **页面加载时** — 先渲染本地缓存（秒开），再拉云端、补发队列
2. **`window.online` 事件** — 网络恢复立即补发
3. **每 60 秒轮询** — 补发队列 + 拉取他人新批注
4. **点「同步」按钮** — 手动立刻补发

## 冲突规则

采用**后写覆盖**（last-write-wins），按 `mark_key` 唯一键 upsert：

- 同一条批注（同段、同侧、同起止）多人修改 → 最后保存的生效
- 不同位置的批注互不影响
- 删除操作优先级最高：队列里的 `delete` 会让本地合并阶段跳过该 key

这条规则简单但会覆盖他人修改。若需要保留历史，把 `annotations` 表改成追加式
（每次修改插新行、`select` 时按 `mark_key` 取 `updated` 最新一条），而不是原地 upsert。

## 队列去重

同一 key 连续修改多次，队列只保留**最后一次**（`queuePush` 里先 `filter` 再 `push`）。
避免离线期间反复改一句备注、联网后被连发十几次。

## 失败处理

- 队列同步时**一条失败就停**，不连环报错，剩余留在队列等下次
- 失败不静默：顶栏显示「N 条待同步」，点「同步」可重试
- 云端写入失败会自动降级到队列，不会丢批注

## 已知限制

| 限制 | 说明 |
|---|---|
| 换浏览器不同步 | localStorage 不跨浏览器。A 电脑离线写的，B 电脑看不到，要等同 A 联网同步后 |
| 清除浏览器数据会丢 | 离线队列只在本机。清缓存/隐私模式关闭 → 队列消失 |
| 隐身模式 | 关闭窗口即清空，不适合离线编辑 |
| 多标签页 | 同一浏览器开两个标签，各自的 `S.marks` 是内存副本，可能短暂不一致；刷新即一致 |

## 改造成"纯本地优先"（可选）

若希望**断网也能首次使用**，把页面改造成 PWA：

1. 加 `manifest.json`（`name` / `start_url` / `display: standalone`）
2. 加 Service Worker 缓存 `index.html` 与 SDK
3. 首次联网打开后，浏览器会装成应用，之后离线也能启动

这不是默认实现，因为会引入 SW 缓存更新问题（改了页面但用户看到的还是旧版）。
需要时再开。
